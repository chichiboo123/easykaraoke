## 0. 요약 (Executive Summary)

로컬 우선(local-first) 정적 웹앱으로서의 골격은 잘 잡혀 있습니다. 의존성 0, 미리보기와 출력이 **동일한 `renderFrame()`을 공유**하는 설계, 5단계 선형 워크플로, IndexedDB 자동 저장은 이 규모의 도구로서 적절한 선택입니다.

그러나 **"완성된 영상"의 품질을 좌우하는 3개 축 — 타이밍 정확도, 가사 하이라이트 정렬, 내보내기 안정성 — 모두에 근본적인 결함**이 있습니다. 특히 아래 5건은 사용자가 만든 결과물이 "쓸 수 있는 노래방 영상"이 되지 못하게 만드는 수준입니다.

| # | 결함 | 영향 |
|---|---|---|
| C-1 | 음절 채우기(fill)가 **글자 위치와 어긋남** (공백 폭 누락) | 모든 결과 영상에서 하이라이트가 왼쪽으로 밀림 |
| C-2 | 모든 음절의 길이가 **0.35초로 고정** (보정 코드가 실행되지 않음) | 긴 음도 0.35초 만에 채워지고 멈춤 → 노래방 기능 상실 |
| C-3 | 내보내기 1회 후 **오디오가 영구히 죽음**, 2회차 내보내기 실패 | 재시도 불가, 새로고침 필요 |
| C-4 | **입력 지연 보정(offset) 없음** | 모든 타이밍이 반응속도+출력지연만큼 늦음 |
| C-5 | 폰트 파일이 **저장소에 하나도 없음** | 6종 글꼴 선택 UI가 전부 동일한 시스템 폰트로 표시 |

## 1. 앱 구조

### 1.1 아키텍처

```
index.html ──▶ app.js (컴파일된 단일 진입점)
                 ├─ types.js      상태 스키마 + newProject()
                 └─ lib/
                     ├─ lyrics.js    Intl.Segmenter 음절 분리 / [배역] 파싱
                     ├─ fonts.js     FontFace 로딩
                     ├─ storage.js   IndexedDB (projects / files 2개 스토어)
                     ├─ frame.js     시간 → 블록/진행률 계산 (순수 함수)
                     ├─ renderer.js  1920×1080 Canvas 2D 그리기
                     └─ exporter.js  captureStream + MediaRecorder 실시간 녹화
```

- **번들러 없음.** `tsc`가 `src/` → `dist/`로 ESM을 그대로 출력하고, 브라우저가 상대경로 import로 로드합니다. 의존성이 없는 프로젝트에서는 합리적입니다.
- **상태 관리**: 모듈 최상위 `let` 변수 12개(`project`, `audioBlob`, `bgImage`, `selected`, `stampIndex`, `step`, `history`, `future` …)에 전역 가변 상태를 둡니다(`src/app.ts:3`).
- **렌더링 모델**: 모든 변경은 `change()` → `editor()` → `shell()` → **`#app.innerHTML` 전체 교체**입니다(`src/app.ts:4,9,34`). 가상 DOM도, 부분 갱신도 없습니다.
- **뷰 = 문자열 템플릿, 이벤트 = 재렌더 후 재바인딩**(`bindAudio`/`bindLyrics`/`bindTiming`/`bindDesign`/`bindExport`).

### 1.2 좋은 점

1. **미리보기 = 출력**: 3단계 미리보기, 4단계 디자인 미리보기, 내보내기가 모두 `renderFrame(ctx, project, time, bg)` 하나를 씁니다. "보이는 대로 나온다"는 가장 중요한 신뢰 요소를 구조적으로 보장합니다.
2. **순수 함수 분리**: `frame.ts`의 `segmentProgress`/`blockAt`은 DOM 의존이 없어 테스트 가능합니다(다만 테스트가 없습니다 — §6).
3. **프라이버시 설계**: 백엔드·분석 SDK·CDN 호출이 전혀 없습니다. 랜딩의 "서버에 업로드되지 않아요" 문구가 실제 코드와 일치합니다.
4. **에러 부트스트랩**: `index.html`의 8초 타임아웃 + `error` 핸들러로 GitHub Pages 배포 실패 시 빈 화면 대신 안내를 띄웁니다.

## 2. UI 문제

### 2.1 치명적 — "놓아주세요"인데 드롭이 안 됨

1단계 업로드 영역은 `MP3, WAV, M4A 또는 AAC 파일을 **놓아주세요**`라고 안내하지만, **`dragover`/`drop` 핸들러가 전혀 없습니다**(`src/app.ts:11,12`). 실제로 파일을 끌어다 놓으면 브라우저가 그 파일로 페이지를 이탈합니다(작업 유실). 동작하는 것은 클릭뿐입니다. — *UI가 거짓말을 하는 케이스.*

### 2.2 6종 글꼴이 전부 같은 모양

- `fonts.ts`는 `./fonts/NotoSansKR-Regular.woff2` 등 6개 파일을 로드하지만 저장소의 `fonts/`, `public/fonts/`에는 **`.gitkeep`만 있습니다.**
- 결과: 6개 로드가 모두 실패 → `console.warn` 한 줄만 남고 **UI에는 아무 표시가 없습니다.** 4단계 글꼴 카드 6개가 `style="font-family:'Jua'"` 등으로 렌더되지만 전부 시스템 기본 산세리프로 보입니다.
- 기본값 `fontFamily:'TJ Joy'`도 존재하지 않아, **아무 설정도 하지 않은 사용자의 결과 영상은 폴백 폰트로 출력**됩니다.
- `public/styles.css`의 `@font-face` 2건도 매 로드 시 404를 냅니다.
- **필요 조치**: 로드 실패한 글꼴 카드는 비활성/배지 표시, 기본값은 실재하는 폰트로.

### 2.3 프리셋 썸네일이 실제 결과와 불일치

CSS 썸네일(`.p-classroom`은 단색 `#34d399`, `.p-stage`는 `#2a184b`)과 렌더러 팔레트(`classroom`: `#0891b2→#34d399`, `stage`: `#16122c→#522278`)가 **하드코딩으로 따로 관리**되어 색이 다릅니다(`public/styles.css`, `src/lib/renderer.ts:2`). 고른 것과 나오는 것이 다릅니다. 또한 6개 프리셋의 차이는 **배경 그라디언트 2색 + 강조색 1개뿐**이며, 레이아웃·타이포그래피·모션 차이는 0입니다. "6개 디자인"이라는 표현이 과장입니다.

### 2.4 키보드로 파일 선택 불가 (접근성)

`<label class="button">…<input type="file"></label>` 패턴에서 input이 `opacity:0; pointer-events:none`입니다. label은 포커스를 받지 못하고 input도 받지 못하므로 **키보드만 쓰는 사용자는 프로젝트 불러오기 / 내 글꼴 추가 / 배경 이미지를 아예 사용할 수 없습니다.** (1단계 오디오 `.drop input`만 `pointer-events:auto`라 예외적으로 동작합니다.)

### 2.5 기타 접근성

- `#app.innerHTML` 전체 교체 후 **포커스 이동/복원이 없습니다.** 스크린리더 사용자는 매 조작마다 문서 처음으로 되돌아갑니다.
- 진행 단계 `nav`에 `aria-current`가 없습니다. 활성 표시가 색상(`#55329d`)에만 의존합니다.
- 미리보기 `<canvas>`에 대체 텍스트·설명이 없습니다.
- 내보내기 진행률(`#percent`, `#stage`)이 `aria-live` 없이 갱신되어 **진행 상황이 음성으로 안내되지 않습니다.**
- `#saved` 배지는 한 번 `✓ 자동 저장됨`이 되면 이후 절대 바뀌지 않아 **저장 중/실패 상태를 신뢰할 수 없습니다.**
- `prefers-reduced-motion` 미지원. 3단계 미리보기 rAF 루프는 **정지 상태에서도 계속 돌아** 배터리를 소모합니다.
- 푸터 12px `#7a7486`는 대비가 경계선입니다.

### 2.6 CSS 구조

`.hero div`, `.player div`, `.stamp div`, `.checklist div`, `.cards article input` 같은 **위치 의존 선택자**가 다수라 마크업을 조금만 바꿔도 레이아웃이 깨집니다. 전역 `button` 규칙이 테두리/배경을 강제해 `.steps button`, `.back` 등에서 매번 되돌리는 구조입니다. 다크 모드 대응은 없습니다.

## 3. UX — 작업 흐름

### 3.1 치명적: 가사 재적용이 모든 타이밍을 말없이 파괴

- 2단계의 **"가사 카드 만들기"** 버튼은 `parseLyrics()` 결과로 `lyricBlocks`를 통째로 교체합니다. 모든 `segment.id`가 새로 발급되고 `start/end`는 0으로 초기화됩니다(`src/app.ts:16`).
- 개별 가사 카드의 텍스트를 수정해도 그 줄의 `segments`가 재생성되어 **해당 줄의 타이밍이 사라집니다.**
- **경고도, 확인 대화상자도, 실행 취소 안내도 없습니다.** 200음절을 찍은 뒤 오타 하나 고치려고 2단계에 들어가면 작업 전체가 날아갑니다.
- Ctrl+Z가 있지만 UI 어디에도 표시되지 않고(3단계 단축키 안내에도 없음), 재렌더 후 되돌리기 대상이 무엇인지도 알 수 없습니다.
- **필요 조치**: 텍스트 diff 기반 병합(변경되지 않은 줄의 타이밍 보존) + 파괴적 변경 시 확인 + 실행 취소 토스트.

### 3.2 치명적: 타이밍 정확도 보정 수단이 전무 (C-4)

`stamp()`는 `audio.currentTime`을 **키 이벤트 처리 시점에** 읽습니다(`src/app.ts:21`).

- `e.timeStamp` 기반 보정 없음 → 이벤트 큐 지연이 그대로 반영됩니다.
- **오디오 출력 지연(하드웨어 버퍼, 블루투스 100~300ms) 보정 없음.**
- **사용자 반응 지연(통상 150~250ms) 보정 옵션 없음.**
- 결과적으로 **모든 스탬프가 체계적으로 늦습니다.** 그런데 전체 오프셋을 일괄 이동시키는 기능이 없어, 사용자는 음절 하나하나를 `±10/50/100ms` 버튼으로 수동 교정해야 합니다.
- **재생 속도 조절이 없습니다**(README는 "원본 속도와 음정을 그대로 사용"이라고 명시). 0.5배속 스탬핑은 정밀 타이밍 입력의 표준 기법인데 사용할 수 없습니다.
- 3단계에 **볼륨 조절이 없습니다**(1단계에만 존재).

### 3.3 스탬핑 중 전체 DOM 재구축

Space 한 번마다 `change()` → `editor()` → `#app.innerHTML` 전체 교체입니다.

- 타임라인은 **음절 1개당 버튼 1개**입니다. 500음절 곡이면 매 타건마다 500개 노드를 파괴/재생성합니다.
- 가장 지연에 민감한 조작에 가장 무거운 렌더를 붙인 구조입니다. 연타 시 프레임 드롭 = 타이밍 오차.
- 타임라인의 **가로 스크롤 위치가 매 타건마다 초기화**됩니다.
- `history.push(structuredClone(project))`도 매 타건마다 실행됩니다.

### 3.4 3단계에서 빠진 기본 기능

- **타임라인 클릭 → 해당 시각으로 이동이 안 됩니다.** 클릭은 선택만 합니다(`src/app.ts:20`). 노래방 편집기에서 가장 기대되는 조작입니다.
- **재생 헤드(playhead) 표시가 없습니다.** 파형에도, 타임라인에도 없습니다.
- 파형(1단계, 100px = 1초 아님)과 타임라인(3단계, 100px = 1초)이 **서로 다른 좌표계**이고 같은 화면에 있지도 않습니다. 두 시각화가 정렬되지 않습니다.
- 타임라인이 **단일 레인**이라 `start=0`인 미입력 음절이 전부 왼쪽 끝에 겹쳐 쌓입니다.
- 드래그로 길이/위치를 조절할 수 없습니다(숫자 입력 + 넛지 버튼뿐).
- **"아직 타이밍이 없는 첫 음절로 이동"이 없습니다.** `stampIndex`는 저장되지 않아 프로젝트를 다시 열면 0으로 돌아가고, 이어서 작업하려면 처음부터 다시 찍어야 합니다.
- `Backspace` 취소는 현재 음절만 0으로 되돌리고 **직전 음절의 `end`는 복구하지 않습니다.**
- Ctrl+Z 후에도 `stampIndex`/`selected`는 스냅샷에 포함되지 않아 **커서가 앞으로 나간 채 남습니다.**

### 3.5 파형

`drawWave()`는 1단계를 렌더할 때마다 **파일 전체를 `decodeAudioData`로 디코드**합니다(캐시 없음, 워커 없음). 8MB MP3 ≈ 50MB PCM을 메인 스레드에서 처리하므로, 1단계로 돌아갈 때마다 수백 ms~수 초 멈춥니다. 캔버스는 `1000×150` 고정 후 CSS로 늘려 **HiDPI에서 흐릿**합니다.

### 3.6 저장 / 파일 관리

- `save()`는 350ms 디바운스 후 **`audioBlob`·`bgBlob`·`fontBlob`을 매번 함께 IndexedDB에 다시 씁니다**(`src/app.ts:34`, `src/lib/storage.ts:3`). 색상 하나만 바꿔도 10MB 오디오를 재기록합니다 → **쓰기 증폭, 디스크/배터리 소모, 할당량 초과 위험.** 파일은 변경 시에만 써야 합니다.
- 저장 실패 시 안내가 `저장 공간을 확인해 주세요` 텍스트 한 줄이며, **어떤 데이터가 유실되는지 알 수 없습니다.**
- 최근 작업은 **6개만 표시**되고, 삭제·이름 변경·검색이 없습니다(§S-4).
- `.mkaraoke`는 **오디오 전체를 base64로 넣은 단일 JSON**입니다(`src/app.ts:30,32,33`). 10MB 음원 → 약 13.4MB 문자열 → `JSON.stringify`/`JSON.parse` 시 수 배의 메모리 피크. 저장/불러오기 중 **진행 표시가 없고 UI가 완전히 멈춥니다.** ZIP 또는 Blob 컨테이너가 적절합니다.
- `importPackage`는 `format`/`version`만 확인하고 **내부 구조를 검증하지 않습니다.** 손상된 파일은 렌더링 중 예외로 이어집니다. 또한 같은 `id`의 기존 프로젝트를 **경고 없이 덮어씁니다.**
- `openRecent`는 `fontBlob`이 있으면 **항상** 사용자 글꼴로 덮어씁니다. 사용자가 나중에 내장 글꼴로 되돌려 저장했더라도 다시 열면 사용자 글꼴로 되돌아갑니다(`src/app.ts:7`).

### 3.7 모바일

- 워크스페이스는 1열로 접히지만, 3단계 타임라인(100px/초)은 사실상 사용 불가입니다.
- 모바일에는 Space 키가 없습니다. "지금 찍기" 버튼이 있는 것은 좋으나, **탭 지연이 커서 정밀도가 더 나빠집니다.**
- iOS Safari는 MP4 MediaRecorder를 제공하지 않아 **내보내기 버튼이 영구 비활성**입니다. 그 사실은 5단계까지 가야 알 수 있습니다 — **랜딩에서 미리 알려야 합니다.**

## 4. 결과물 생성 과정 (내보내기)

### 4.1 치명적: 1회 내보내기 후 오디오가 죽는다 (C-3)

`exportVideo()`는 매 호출마다 `new AudioContext()` → `ac.createMediaElementSource(audio)`를 실행합니다(`src/lib/exporter.ts:4`).

- **HTMLMediaElement는 평생 단 하나의 `MediaElementAudioSourceNode`에만 연결될 수 있습니다.** 두 번째 내보내기는 `InvalidStateError`로 실패합니다.
- 더 나쁜 것은, 한 번 소스 노드에 연결되면 그 요소의 오디오 출력은 **영구히 그 그래프로 라우팅**됩니다. 내보내기 후 `await ac.close()`가 실행되면 **전역 `audio` 요소가 그 세션 내내 무음**이 됩니다 → 3단계 미리보기 재생도 소리가 안 납니다.
- **취소 경로는 더 심각합니다.** `AbortError`로 reject할 때 `stream`/`source`/`ac`를 **전혀 정리하지 않습니다.** 취소 한 번이면 앱을 새로고침해야 합니다.
- **필요 조치**: `MediaElementAudioSourceNode`를 모듈 수준에서 1회만 생성해 재사용하거나, 내보내기용으로 별도의 `Audio` 인스턴스를 만들 것. 그리고 `finally` 블록에서 항상 정리할 것.

### 4.2 실시간 rAF 녹화의 구조적 한계

```
rec.start(1000) → audio.play() → requestAnimationFrame(tick) → audio.ended 시 rec.stop()
```

- **곡 길이만큼 그대로 걸립니다.** 4분 곡 = 4분 대기. 오프스크린 렌더 + `WebCodecs`(`VideoEncoder`/`AudioEncoder` + `mp4-muxer`)를 쓰면 실시간보다 훨씬 빠르고 프레임 정확하게 만들 수 있습니다.
- **탭을 백그라운드로 보내면 `requestAnimationFrame`이 멈춥니다.** 캔버스 갱신이 정지 → **화면이 얼어붙은 영상**이 되고, `audio.ended` 검사도 멈춰 **녹화가 끝나지 않습니다.** 이에 대한 경고가 UI에 없습니다.
- `captureStream(30)`은 rAF가 그리는 대로 캡처하므로 **가변 프레임레이트(VFR)** 출력이 되기 쉽고, 편집기에서 다시 열 때 A/V 동기가 어긋날 수 있습니다. `canvas.captureStream(0)` + `track.requestFrame()`으로 프레임을 능동 제어하는 편이 안정적입니다.
- `rec.start()`가 **첫 그리기 전에** 호출됩니다. 첫 프레임이 빈 캔버스로 잡혀 **시작부에 검은 깜빡임**이 생길 수 있습니다.
- 내보내는 동안 `source.connect(ac.destination)`이 살아 있어 **곡이 스피커로 그대로 재생**됩니다. 음소거 옵션이 없습니다.
- `audio.ended` 시 즉시 `rec.stop()` → **꼬리 여백이 0.** 마지막 음절의 채우기와 엔딩이 뚝 잘립니다(`ending` 마커 타입은 존재하지만 렌더러가 처리하지 않습니다).
- 해상도/비트레이트/fps가 **1920×1080 / 8Mbps / 30fps로 하드코딩**되어 있습니다. 저사양 PC용 720p 옵션이 없습니다.

### 4.3 브라우저 지원 판정이 지나치게 엄격

`exportSupport()`는 `video/webm;codecs=vp9,opus`도 후보로 두지만, UI는 `s.type.includes('mp4')`가 아니면 **버튼을 비활성화**합니다(`src/app.ts:28`). Firefox 사용자는 WebM으로 충분히 만들 수 있는데도 **완전히 차단**됩니다. 또한 `exportVideo`는 WebM Blob을 정상 반환하도록 작성돼 있는데 다운로드 파일명은 **항상 `.mp4`로 하드코딩**되어 있습니다(도달 시 확장자 불일치).

### 4.4 내보내기 게이트가 전부 아니면 전무

`timed !== total`이면 버튼이 비활성입니다. **일부만 타이밍을 넣고 시험 렌더를 해볼 수 없습니다.** 300음절 중 299개를 찍어도 결과물을 볼 수 없습니다. 미완성 음절을 회색 처리하는 부분 렌더링을 허용해야 합니다.

### 4.5 진행률 / 오류

- 진행률은 `audio.currentTime / duration`이므로 **인코딩 지연을 반영하지 않습니다.** 99%에서 오래 멈춘 것처럼 보일 수 있습니다.
- 남은 시간(ETA) 표시가 없습니다. 실시간 녹화이므로 ETA는 정확히 계산 가능한데도 제공하지 않습니다.
- `MediaRecorder`가 중간에 실패하면(디스크 부족 등) `chunks`가 조용히 유실됩니다.

## 5. 결과물(영상) 품질

### 5.1 치명적: 하이라이트가 글자와 어긋난다 (C-1)

`src/lib/lyrics.ts:3`의 `segmentKorean()`은 **공백을 완전히 버립니다**(`if(/^\s+$/u.test(c)) continue`).
반면 `src/lib/renderer.ts:5`의 `drawLyric()`은:

```js
ctx.fillText(b.text, 960, y);                    // ← 공백 포함 원문을 그림
let x = 960 - ctx.measureText(b.text).width / 2; // ← 공백 포함 폭으로 시작점 계산
for (const s of b.segments) {                    // ← 공백 없는 음절들
  const w = ctx.measureText(s.text).width;
  ... x += w;                                    // ← 공백 폭만큼 매번 뒤처짐
}
```

즉 **그려진 글자에는 공백이 있고, 채우기 커서는 공백을 건너뛰며 전진**합니다. 공백이 3개 있는 줄이라면 줄 끝에서 하이라이트가 **공백 3칸 폭만큼 왼쪽으로 밀립니다.** 한국어 가사는 거의 항상 띄어쓰기를 포함하므로 **사실상 모든 결과 영상에서 발생**합니다.

**해결**: 세그먼트에 원문 오프셋(`charStart`/`charEnd`)을 보존하고, `x` 전진을 원문 부분문자열 측정으로 계산할 것.

### 5.2 치명적: 모든 음절이 0.35초 고정 (C-2)

`src/app.ts:21`:

```js
if (stampIndex > 0) {
  const prev = a[stampIndex-1].segment;
  if (prev.end <= prev.start) prev.end = Math.max(prev.start + .05, now); // ← 절대 실행 안 됨
}
s.start = now;
s.end = now + .35;   // ← end는 이미 start보다 크게 설정됨
```

직전 스탬프가 이미 `end = start + 0.35`를 넣었으므로 `prev.end <= prev.start`는 **항상 거짓**입니다. 다음 음절이 찍힐 때 이전 음절의 끝을 늘리는 보정이 **한 번도 동작하지 않습니다.**

결과: 길게 끄는 음(2초짜리 "사~랑~")도 **0.35초 만에 채워지고 나머지 1.65초는 정지**합니다. 반대로 빠른 음절은 다음 음절과 겹칩니다. **노래방 영상의 핵심 기능인 "음의 길이만큼 차오르는 표시"가 성립하지 않습니다.**

**해결**: `prev.end = Math.max(prev.start + 0.05, now)`를 무조건 적용(다음 스탬프가 이전 음절의 끝을 확정), 마지막 음절만 기본 길이를 사용.

### 5.3 긴 가사가 잘리거나 넘친다

- `fit()`은 96px에서 **42px까지만** 축소합니다(`src/lib/renderer.ts:4`). 42px에서도 1650px를 넘는 긴 줄은 **좌우로 화면 밖까지 흘러넘칩니다.** 줄바꿈(word wrap) 로직이 전혀 없습니다.
- **다음 가사 미리보기(66px, y=680)에는 `fit()`이 적용되지 않습니다** → 긴 다음 줄은 무조건 넘칩니다.
- **배역 배지는 `(850, 250, 220×65)` 고정 크기**입니다(`rounded(...)`). "앙상블 전체" 같은 긴 배역명은 배지 밖으로 삐져나옵니다. 텍스트 폭 측정이 없습니다.

### 5.4 배경 이미지가 찌그러진다

`ctx.drawImage(bg, -20, -20, 1960, 1120)` — **원본 종횡비를 무시하고 강제로 늘립니다**(`src/lib/renderer.ts:6`). 세로 사진이나 정사각 이미지를 넣으면 그대로 왜곡됩니다. cover/contain 계산이 필요합니다.

또한 `ctx.filter`(brightness/blur)는 브라우저 지원 편차가 있고, **1960px 이미지에 blur 필터를 매 프레임(30fps) 적용**하는 것은 내보내기 성능에 직접 타격을 줍니다. 배경은 한 번만 오프스크린 캔버스에 전처리해야 합니다.

### 5.5 시작/끝 처리

- 타이밍이 하나도 없으면 `blockAt()`이 **마지막 블록**을 반환합니다(`src/lib/frame.ts:3`: 두 조건 모두 실패 시 `index = length-1`). 4단계 디자인 미리보기에서 **첫 줄이 아니라 마지막 줄이 보입니다.** 혼란스럽습니다.
- 인트로 카드는 `time < first && time < max(first, 6)` 조건으로 표시됩니다. 첫 가사가 30초 뒤면 **30초 내내 제목 카드만 나옵니다.** 반대로 첫 가사가 2초면 카드가 2초만 스칩니다. 노출 시간 제어가 없습니다.
- 인트로 구간에 **"곧 시작합니다" 카운트다운이 없습니다**(마커 UI 부재로 카운트다운 기능 자체가 도달 불가 — §S-5). 노래방 영상의 필수 요소입니다.
- 간주(interlude) 화면도 같은 이유로 사용할 수 없습니다.

### 5.6 가독성

- 상단 메타(작품명·곡번호·제목)는 `rgba(255,255,255,.8)`로만 그려지고 **외곽선이 없습니다.** 밝은 배경 이미지에서는 읽히지 않습니다(어둡게 슬라이더에만 의존).
- 카운트다운 숫자, 간주 라벨도 외곽선 없이 흰색입니다.
- 미리보기 캔버스는 `devicePixelRatio`를 반영하지 않아 **레티나에서 흐릿**합니다. (최종 출력은 1920×1080 실제 해상도라 영향 없음.)

### 5.7 언어

`Intl.Segmenter('ko', {granularity:'grapheme'})`를 고정 사용합니다. **영어 가사는 알파벳 한 글자씩 타이밍 단위가 됩니다** ("Love" → L/o/v/e 4스탬프). 뮤지컬 넘버에 영어 구절이 섞이는 경우가 흔한데 단어 단위 모드가 없습니다.
