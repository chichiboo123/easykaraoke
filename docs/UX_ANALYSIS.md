# 여기 있어 노래방 — UI/UX 분석

작성일: 2026-09-09 · 대상 브랜치: `claude/karaoke-app-ui-ux-analysis-pypm1r`
분석 범위: `src/app.ts`, `src/lib/*.ts`, `src/types.ts`, `public/styles.css`, `index.html`

> 이 문서는 **UI/UX 관점**에 집중합니다. 개별 버그 목록과 재현 조건은 [`APP_ANALYSIS.md`](./APP_ANALYSIS.md)를 참고하세요.

## 0. 요약

이 앱은 **구조가 나쁜 게 아니라 구조의 대가를 사용자가 치르고 있습니다.**

- 의존성 0, 번들러 없음, 백엔드 없음 — 로컬 우선 도구로서 매우 좋은 선택입니다.
- 미리보기와 최종 출력이 **같은 `renderFrame()`을 공유**합니다. "보이는 대로 나온다"는 신뢰를 구조적으로 보장하는 설계입니다.

그런데 이 두 강점 위에 얹힌 **렌더링 모델(전체 `innerHTML` 교체)과 정보 구조(5단계 선형 마법사)** 가, 하필이면 이 앱에서 가장 중요한 작업인 **"음악을 들으며 타이밍을 찍는 일"** 을 정면으로 방해합니다.

세 문장으로 요약하면:

1. **어려운 이유** — 타이밍 작업에 필요한 도구(파형·재생헤드·시크·볼륨·속도)가 다섯 화면에 흩어져 있고, Space를 누를 때마다 화면 전체가 다시 만들어져 설정과 스크롤이 초기화됩니다.
2. **불편한 이유** — 디자인 토큰이 하나도 없어 보라색 9종·회색 8종·테두리색 9종이 제각각이고, 밝은 편집 화면 속에 어두운 결과 캔버스가 이물질처럼 박혀 있습니다.
3. **개선 방향** — 3단계를 "한 화면 스튜디오"로 승격하고, 부분 갱신 렌더링과 CSS 변수 기반 토큰 시스템을 도입하면 위 두 문제의 대부분이 함께 해결됩니다.

## 1. 앱 구조

### 1.1 구성

```
index.html
  └─ app.js (단일 진입점, 번들러 없음)
       ├─ types.js      상태 스키마 · newProject()
       └─ lib/
           ├─ lyrics.js    Intl.Segmenter 음절 분리 · [배역] 파싱
           ├─ fonts.js     FontFace 로딩
           ├─ storage.js   IndexedDB (projects / files)
           ├─ frame.js     시간 → 블록·진행률 (순수 함수)
           ├─ renderer.js  1920×1080 Canvas 2D
           └─ exporter.js  captureStream + MediaRecorder 실시간 녹화
```

### 1.2 상태와 렌더링 모델

`src/app.ts:3`에 모듈 전역 가변 변수 12개가 있습니다.

```ts
let project, audioBlob, bgBlob, fontBlob, audioUrl, bgUrl,
    bgImage, selected, stampIndex, step, history, future
```

모든 변경은 **하나의 경로**를 지나갑니다.

```
사용자 조작 → change(fn) → history.push(structuredClone(project))
            → fn() → save() → editor() → shell() → $('#app').innerHTML = 전체 문자열
```

즉 **부분 갱신이 없습니다.** 색상 하나를 바꾸든 Space를 한 번 누르든, 문서 전체가 파괴되고 다시 만들어집니다. 이 한 줄이 이후 §2의 문제 대부분의 원인입니다.

### 1.3 화면 구조

| 단계 | 함수 | 그 단계에만 있는 도구 |
|---|---|---|
| 1. 반주 | `audioStep` | **파형, 시크바, 볼륨** |
| 2. 가사 | `lyricsStep` | 뮤지컬 모드 토글, 배역 색상, 가사 카드 |
| 3. 타이밍 | `timingStep` | 스탬프 패널, 미리보기, A–B 반복, 확대, 타임라인, 인스펙터 |
| 4. 디자인 | `designStep` | 프리셋 6, 글꼴 6, 배경·밝기·어둡게·흐림, 미리보기 |
| 5. 내보내기 | `exportStep` | 체크리스트, MP4 만들기, 프로젝트 파일 저장 |

**굵게 표시한 항목이 문제의 핵심입니다.** 타이밍을 찍는 3단계에 파형도, 시크바도, 볼륨도 없습니다.

## 2. 반주 제작 과정이 어려운 이유

### 2.1 작업 도구가 작업 화면에 없다

실제 작업은 `듣기 → 찍기 → 확인 → 고치기`의 **반복**인데, UI는 이것을 다섯 개의 **일방향 단계**로 잘라 놓았습니다. 그 결과 3단계(타이밍)에서 다음이 불가능합니다.

- **파형을 볼 수 없습니다.** 파형은 1단계에만 있습니다(`audioStep`). 어디가 전주이고 어디서 노래가 시작되는지 보면서 찍을 수 없습니다.
- **시크바가 없습니다.** 3단계에서 특정 지점으로 이동하려면 A–B 반복 입력란에 숫자를 직접 입력하는 방법뿐입니다.
- **볼륨 조절이 없습니다.** 1단계에만 있습니다.
- **재생 위치를 숫자로만 압니다.** `<output id="timing-clock">`의 `00:42.310` 텍스트가 전부입니다.

즉 사용자는 **1단계에서 곡 구조를 파악하고, 그 기억을 들고 3단계로 넘어가** 눈으로 확인할 수 없는 상태에서 Space를 눌러야 합니다.

### 2.2 타임라인이 시간을 읽을 수 없다

`.timeline`은 시간 축처럼 생겼지만 시간 정보가 없습니다.

- **재생 헤드가 없습니다.** 지금 어디를 재생 중인지 타임라인 위에 표시되지 않습니다.
- **눈금과 시간 라벨이 없습니다.** 배경은 `repeating-linear-gradient`로 그린 100px 격자뿐이고, 숫자가 하나도 없습니다.
- **클릭해도 이동하지 않습니다.** `bindTiming`의 `[data-seg]` 핸들러는 `selected`만 바꾸고 `editor()`를 부릅니다. 노래방 편집기에서 가장 먼저 기대하는 조작인데 없습니다.
- **미입력 음절이 전부 겹쳐 쌓입니다.** 타이밍 전 `start = 0`이므로 모든 음절이 `left: 0`에 놓입니다. 작업 초반 타임라인은 왼쪽 끝의 검은 덩어리 하나입니다. 진행 상황을 시각적으로 읽을 수 없습니다.
- **드래그 편집이 없습니다.** 길이·위치 조절은 숫자 입력과 `±10/50/100ms` 버튼 6개뿐입니다.

### 2.3 Space를 누를 때마다 작업 환경이 초기화된다

이것이 가장 실질적인 고통입니다. `stamp()` → `change()` → `editor()` → `innerHTML` 전체 교체이므로, **Space 한 번에 다음이 모두 리셋됩니다.**

| 리셋되는 것 | 원인 |
|---|---|
| **A–B 반복 체크박스** | `<input id="loop-on" type="checkbox">` — `checked` 속성이 템플릿에 없음 |
| **A 지점** | `value="0"` 하드코딩 |
| **B 지점** | `value="${Math.min(10, duration)}"` 하드코딩 |
| **확대 슬라이더** | `value="100"` 하드코딩 |
| 타임라인 가로 스크롤 위치 | DOM 노드가 새로 생성됨 |
| 포커스 | 문서 전체가 교체됨 |

**A–B 구간 반복은 타이밍 작업의 표준 기법인데, 이 앱에서는 Space를 한 번 누르는 순간 꺼집니다.** 구간 반복을 켜고 그 안에서 여러 음절을 찍는 것이 원천적으로 불가능합니다.

여기에 성능 문제가 겹칩니다. 타임라인은 **음절 1개 = DOM 버튼 1개**입니다. 500음절 곡이면 타건 한 번마다 500개 노드를 파괴하고 재생성하며, 동시에 `structuredClone(project)`와 IndexedDB 저장(오디오 Blob 포함)이 돌아갑니다. **가장 지연에 민감한 조작에 가장 무거운 연산을 붙인 구조**이고, 연타 시 프레임 드롭은 그대로 타이밍 오차가 됩니다.

부수적으로 재생 버튼도 어긋납니다. `#timing-play`는 `▶`/`Ⅱ`를 `editor()` 시점의 `audio.paused`로 결정하는데, 버튼 클릭은 재렌더를 부르지 않습니다. **재생 중인데 버튼은 계속 `▶`로 남습니다.**

### 2.4 정밀도를 확보할 수단이 없다

노래방 타이밍은 두 가지 지연이 반드시 끼어듭니다.

- 사람의 반응 지연: 150–250ms
- 오디오 출력 지연: 유선 20–40ms, 블루투스 100–300ms

`stamp()`는 키 이벤트 처리 시점에 `audio.currentTime`을 그대로 읽습니다(`e.timeStamp` 보정 없음). 따라서 **모든 스탬프가 체계적으로 늦습니다.** 그런데,

- **전역 오프셋 조절이 없습니다.** 전체를 한 번에 앞당길 방법이 없어, 음절 하나하나를 `±10/50/100ms` 버튼으로 수동 교정해야 합니다. 300음절이면 수백~수천 번의 클릭입니다.
- **재생 속도 조절이 없습니다.** 0.5배속 스탬핑은 정밀 타이밍 입력의 표준 기법인데, 1단계 설명에 `원본 속도와 음정을 그대로 사용합니다`라고 명시적으로 못 박혀 있습니다.

결과적으로 **"고치는 비용 > 다시 찍는 비용"** 이 되어, 사용자는 마음에 들 때까지 처음부터 다시 찍게 됩니다.

### 2.5 되돌릴 수 없다는 공포

2단계의 **"가사 카드 만들기"** 버튼은 `parseLyrics()` 결과로 `lyricBlocks`를 통째로 교체합니다. 모든 `segment.id`가 새로 발급되고 `start`/`end`가 0이 됩니다. 개별 가사 카드의 텍스트를 한 글자만 고쳐도 그 줄의 `segments`가 재생성됩니다.

- **경고도, 확인 대화상자도, 손실 규모 안내도 없습니다.**
- Ctrl+Z가 있지만 **UI 어디에도 표시되지 않습니다.** 3단계 단축키 안내 줄에도 `Space`, `K`, `Backspace`, `←→`, `Shift`만 있고 되돌리기는 없습니다.

200음절을 찍은 뒤 오타 하나를 고치려고 2단계에 들어가면 작업 전체가 사라집니다. 이 사실을 사용자는 **한 번 잃어보고 나서야** 배웁니다.

### 2.6 중단하고 이어서 할 수 없다

- `stampIndex`가 **프로젝트에 저장되지 않습니다.** 모듈 전역 변수라서 프로젝트를 다시 열면 0으로 돌아갑니다. "어디까지 찍었더라"를 사용자가 기억해야 합니다.
- **"타이밍이 없는 첫 음절로 이동" 버튼이 없습니다.**
- `Backspace` 취소는 현재 음절만 0으로 되돌리고 **직전 음절의 `end`는 복구하지 않습니다.**

4분짜리 곡을 한자리에서 끝까지 찍어야 하는 **all-or-nothing 세션**입니다.

### 2.7 중간 확인이 막혀 있다

5단계의 MP4 버튼은 `timed !== total`이면 비활성입니다. **300음절 중 299개를 찍어도 결과물을 볼 수 없습니다.** 게다가 내보내기는 실시간 녹화라 4분 곡이면 4분을 기다려야 합니다.

즉 사용자는 **모든 작업을 끝낸 뒤 4분을 기다려야 비로소 자기 작업이 제대로 됐는지 확인**할 수 있습니다. 잘못됐다면 다시 처음부터입니다. 피드백 루프가 이보다 나빠지기 어렵습니다.

### 2.8 UI가 사실과 다른 말을 한다

가장 중요한 강점(미리보기 = 출력)을 **UI 표층이 스스로 깎아먹고 있습니다.**

| UI가 말하는 것 | 실제 |
|---|---|
| `MP3, WAV, M4A 또는 AAC 파일을 **놓아주세요**` | `dragover`/`drop` 핸들러가 **한 곳도 없습니다.** 실제로 놓으면 브라우저가 그 파일로 페이지를 이탈합니다 — **작업 유실** |
| 글꼴 6종 선택 카드 | `fonts/`, `public/fonts/`에 `.gitkeep`만 있습니다. 6종이 전부 같은 시스템 폰트로 보이고, 실패 표시도 없습니다 |
| 기본 글꼴 `TJ Joy` | 존재하지 않아 아무 설정도 안 한 사용자의 결과 영상이 폴백 폰트로 나갑니다 |
| 프리셋 썸네일 색 | CSS(`.p-classroom` = `#34d399` 단색)와 렌더러(`classroom` = `#0891b2 → #34d399` 그라디언트)가 따로 하드코딩되어 **고른 색과 나오는 색이 다릅니다** |
| `✓ 자동 저장됨` 배지 | 한 번 그렇게 바뀌면 이후 절대 변하지 않습니다. 저장 중·실패를 구분할 수 없습니다 |
| 오류 안내 | 전부 `alert()` 7곳. 스타일 불가, 맥락 상실, 모달 차단 |

### 2.9 결과가 노래방처럼 보이지 않는다

**과정이 어렵다고 느끼게 하는 가장 깊은 원인은, 열심히 해도 결과가 기대와 다르다는 것입니다.** 그러면 사용자는 도구를 의심하지 않고 **자기 입력을 의심하고 다시 찍습니다.**

**(가) 모든 음절이 0.35초로 고정됩니다.**

```js
if (stampIndex > 0) {
  const prev = a[stampIndex-1].segment;
  if (prev.end <= prev.start)             // ← 항상 false
    prev.end = Math.max(prev.start+.05, now);
}
s.start = now;
s.end = now + .35;                        // ← 이미 end > start로 만들어 둠
```

직전 스탬프가 이미 `end = start + 0.35`를 넣었으므로 `prev.end <= prev.start`는 **한 번도 참이 되지 않습니다.** 다음 음절이 이전 음절의 끝을 확정하는 보정이 **영원히 실행되지 않습니다.**

결과: 2초 동안 끄는 `사~랑~`도 0.35초 만에 다 차오르고 1.65초 동안 멈춰 있습니다. **노래방의 핵심인 "음 길이만큼 차오르는 표시"가 성립하지 않습니다.**

**(나) 하이라이트가 글자와 어긋납니다.**

`segmentKorean()`은 공백을 버리고(`if(/^\s+$/u.test(c)) continue`), `drawLyric()`은 공백이 포함된 원문을 그린 뒤 시작 x를 **공백 포함 폭**으로 계산합니다. 그리고 공백이 없는 음절 폭만 더해가며 전진합니다. 결과적으로 **줄에 공백이 3개면 하이라이트가 공백 3칸 폭만큼 왼쪽으로 밀립니다.** 한국어 가사는 거의 항상 띄어쓰기가 있으므로 **사실상 모든 결과 영상에서 발생합니다.**

**(다) 카운트다운이 없습니다.** `Marker` 타입과 렌더러의 인트로·간주·카운트다운 로직은 구현되어 있지만 **마커를 만드는 UI가 다섯 단계 어디에도 없습니다.** `markers`는 항상 빈 배열이고, 노래방의 필수 요소인 "곧 시작합니다" 카운트다운은 도달할 수 없는 죽은 코드입니다.

### 2.10 환경 제약을 늦게 알려준다

- iOS Safari는 MP4 `MediaRecorder`를 제공하지 않습니다. **내보내기 버튼이 영구 비활성**인데, 그 사실을 **5단계까지 가서야** 알게 됩니다.
- 3단계 타임라인은 `100px = 1초`라 모바일에서 사실상 사용 불가입니다.
- 모바일에는 Space 키가 없습니다. `지금 찍기` 버튼이 있지만 탭 지연이 더 커서 정밀도가 나빠집니다.

## 3. 디자인이 보기 불편한 이유

### 3.1 디자인 토큰이 하나도 없다

`public/styles.css`에 **CSS 변수(`--`)가 `--zoom` 하나뿐**입니다. 색이 전부 리터럴로 흩어져 있고, 그래서 통일될 수가 없습니다.

**보라 계열 9종** — 거의 같지만 미묘하게 다릅니다.

```
#392677 브랜드   #4e3294 primary   #54359c hero em   #55329d 활성 단계
#6546ac 선택됨   #6848b8 eyebrow   #4b3a7c 푸터링크  #6046a8 파형
#563b98 체크리스트  #4f3296 스탬프  #6b45ad 글꼴 배지
```

**회색 8종**: `#5f6673 #5c6677 #64748b #686273 #6d6876 #737080 #7a7486 #858092`
**테두리 9종**: `#e8e5ef #e7e4ec #d7d1e3 #cbc6d5 #c9c0de #ddd6ea #e5e1ea #ddd8e7 #ddd6e8`

사용자는 이걸 "색이 20종이네"라고 인식하지 않습니다. **"뭔가 미묘하게 어수선하다"** 고 느낍니다. 그 정체가 이것입니다.

### 3.2 간격 체계가 없다

margin/padding 값이 `4, 5, 6, 7, 8, 9, 10, 12, 13, 14, 15, 16, 18, 20, 22, 24, 25, 28, 30, 35, 55, 70, 80px` — **8pt 그리드 같은 스케일이 전혀 없습니다.** 폰트 크기도 `12, 13, 19, 20, 22, 32, 38, 54, 72px`로 산발적입니다.

요소마다 여백이 1–3px씩 미묘하게 다르면 사람 눈에는 **"정렬이 안 맞아 보인다"** 로 읽힙니다.

### 3.3 편집 화면과 결과물이 완전히 다른 세계다

```css
body { background: #faf9fc }                      /* 밝은 라벤더 화이트 */
.timing-grid canvas { background: #10172b }       /* 어두운 무대 */
```

노래방 결과물은 어둡습니다. 그런데 편집 도구는 밝습니다. 그래서,

- 어두운 캔버스가 밝은 페이지 위에 **이물질처럼 박혀** 보입니다.
- 밝은 배경 옆에서는 **영상의 어두운 색감을 정확히 판단할 수 없습니다.** 배경 밝기·어둡게·흐림 슬라이더를 조절해도 실제 결과가 어떻게 보일지 감이 오지 않습니다.
- 눈이 캔버스에 집중하지 못합니다. 화면의 주인공이 되어야 할 미리보기가 흰 카드 안의 작은 사각형입니다.
- **다크 모드 대응이 0입니다.** 어두운 방에서 영상 편집을 하는 전형적인 사용 맥락과 정반대입니다.

### 3.4 시각 위계가 평평하다

`.editor { background:#fff; border:1px solid #e5e1ea; border-radius:14px }` 흰 카드 하나 안에 제목·설명문·컨트롤·캔버스·타임라인이 **구분 없이 세로로 쌓입니다.** 섹션 구분선도, 배경 톤 차이도, 그룹 헤더도 거의 없습니다.

특히 4단계(`designStep`)는 한 장에 **프리셋 6개 + 글꼴 6개 + 글꼴 추가 + 설정 6개 컨트롤 + 미리보기 캔버스**가 전부 들어갑니다. 눈이 쉴 곳이 없고, 무엇부터 만져야 할지 알 수 없습니다.

### 3.5 버튼이 전부 같아 보인다

```css
.primary, .button, button { border:1px solid #d7d1e3; border-radius:9px; background:#fff }
```

전역 `button` 규칙이 **모든 버튼을 같은 흰 알약**으로 만듭니다. 그래서 곳곳에서 되돌려야 합니다.

```css
.steps button { border:0; background:none }   /* 되돌리기 */
.back         { border:0; background:none }   /* 되돌리기 */
.chosen       { border:3px solid #6546ac !important }   /* !important로 이기기 */
```

결과적으로 `가사 입력하기 →`, `음절 분리`, `취소`, `↑`, `프로젝트 불러오기`가 **시각적 무게가 같습니다.** 위계가 `primary` / 나머지 2단계뿐이고, secondary·ghost·destructive 구분이 없습니다.

비활성 상태도 문제입니다. `.primary:disabled { background:#aaa }` — `#aaa` 위의 흰 글씨는 대비가 부족하고, **왜 비활성인지 설명이 없습니다.** 5단계 MP4 버튼이 회색인 이유는 사용자가 옆 체크리스트를 스스로 대조해야 알 수 있습니다.

### 3.6 3단계 레이아웃이 시선을 찢는다

```css
.timing-grid { grid-template-columns: 300px 1fr }
.stamp strong { font-size: 72px }
.stamp div    { height: 50px }
```

- 왼쪽 스탬프 패널에 **다음 음절이 72px**로, 오른쪽 미리보기 캔버스 **안에도 같은 가사**가 크게 나옵니다. **같은 정보가 서로 다른 크기·색·위치로 두 번** 나타납니다.
- 72px는 화면에서 가장 큰 요소인데 담고 있는 정보는 **글자 1–2개**입니다. 화면 면적 배분이 정보량과 반대입니다.
- `.stamp div { height:50px }` 고정 안에 다음 음절 5개를 22px로 넣습니다. 넘치면 잘립니다.
- 정작 시선을 둬야 할 곳(파형·재생 위치)은 이 화면에 없습니다(§2.1).

### 3.7 타임라인이 읽히지 않는다

```css
.timeline { height:130px }
.segment  { top:35px; padding:10px 2px; border-width:0 0 5px }
```

- 배역 구분이 **아래쪽 5px 테두리 한 줄**뿐입니다. 130px 높이 중 구분에 쓰는 건 5px입니다.
- 좌우 패딩이 `2px`라 짧은 음절은 글자가 테두리에 붙습니다.
- `min-width:34px` 때문에 짧은 음절끼리 **겹쳐서** 보입니다.
- 시간 라벨이 없어 격자가 무엇을 나타내는지 알 수 없습니다.

### 3.8 위치 의존 선택자가 디자인 개선을 막는다

```css
.hero div          /* 버튼 묶음 */
.player div        /* 재생 컨트롤 줄 */
.player div label { margin-left:auto }
.stamp div         /* 다음 음절 목록 */
.checklist div     /* 체크 항목 */
.cards article input
.role input:last-child
```

스타일이 **마크업 순서에 묶여** 있습니다. 문자열 템플릿에서 `<div>` 하나만 옮기거나 추가해도 레이아웃이 조용히 깨집니다. **"디자인을 고치기 어려운 디자인"** 의 구조적 원인이고, 이 문서의 개선안이 실행되기 어려운 이유이기도 합니다.

### 3.9 결과 영상의 디자인 문제

- **프리셋 6종의 차이가 배경 그라디언트 2색 + 강조색 1색뿐입니다**(`palettes`). 레이아웃·타이포그래피·모션 차이는 0입니다. "6개 디자인"은 과장이고, 사용자가 하나를 고를 이유가 없습니다.
- **가사 줄바꿈이 없습니다.** `fit()`은 96px에서 42px까지만 축소하고, 42px에서도 1650px를 넘는 긴 줄은 **화면 밖으로 흘러넘칩니다.**
- **다음 가사(66px, y=680)에는 `fit()`이 적용되지 않습니다.** 긴 다음 줄은 무조건 넘칩니다.
- **배역 배지가 `(850, 250, 220×65)` 고정 크기**입니다. `앙상블 전체` 같은 긴 배역명은 배지 밖으로 삐져나옵니다.
- **배경 이미지가 찌그러집니다.** `drawImage(bg, -20, -20, 1960, 1120)` — 원본 종횡비를 무시합니다. 세로 사진을 넣으면 그대로 늘어납니다.
- **상단 메타(작품명·곡번호·제목)에 외곽선이 없습니다.** `rgba(255,255,255,.8)`만이라 밝은 배경 이미지에서는 읽히지 않습니다.
- **미리보기 캔버스가 `devicePixelRatio`를 반영하지 않습니다.** 960×540을 CSS로 확대하므로 고해상도 화면에서 흐릿합니다. 사용자는 "결과물도 흐릿하겠구나"라고 오해합니다.
- **타이밍이 없으면 마지막 줄이 보입니다.** `blockAt()`이 두 조건 모두 실패 시 `index = length-1`을 반환하므로, 4단계 디자인 미리보기에 **첫 줄이 아니라 마지막 줄**이 나옵니다.

### 3.10 접근성

- **재렌더 후 포커스가 복원되지 않습니다.** `innerHTML` 전체 교체이므로 스크린리더 사용자는 매 조작마다 문서 처음으로 돌아갑니다.
- **키보드로 파일을 선택할 수 없습니다.** `.button input { opacity:0; pointer-events:none }` 패턴에서 label도 input도 포커스를 받지 못합니다. **프로젝트 불러오기 / 내 글꼴 추가 / 배경 이미지**를 키보드만으로는 아예 쓸 수 없습니다. (1단계 오디오 `.drop input`만 `pointer-events:auto`라 예외적으로 동작합니다.)
- `nav.steps`에 `aria-current`가 없고, 활성 표시가 **색(`#55329d`)에만** 의존합니다.
- 미리보기 `<canvas>`에 대체 텍스트·설명이 없습니다.
- 내보내기 진행률(`#percent`, `#stage`)이 `aria-live` 없이 갱신되어 **진행 상황이 음성으로 안내되지 않습니다.**
- 푸터 12px `#7a7486` on `#faf9fc`는 소형 텍스트 기준 대비가 경계선입니다.
- `prefers-reduced-motion` 미지원. 3단계 rAF 루프는 **정지 상태에서도 계속 돌아** 배터리를 소모합니다.

### P1 — 작업 자체를 가능하게

**6. 3단계를 "한 화면 스튜디오"로 승격** — 가장 큰 개선입니다.

```
┌──────────────── 미리보기 (16:9) ─────────────────┐
│                                                  │
├──── 트랜스포트 ───────────────────────────────────┤
│ ▶  00:42.310 / 03:20   0.5× 0.75× 1×   🔊 ────   │
├──── 파형 + 재생헤드 + 시간 눈금 ──────────────────┤
│ ▁▃▅█▆▃▁▂▅█▇▄▁ ┃                                  │
├──── 음절 타임라인 (같은 좌표계로 세로 정렬) ─────┤
│ 우 리 함 께  ┃ 문 을  열 어                        │
├──── 대기열: 아직 찍지 않은 음절 ─────────────────┤
└──────────────────────────────────────────────────┘
```

- 파형과 타임라인을 **같은 시간 좌표계로 세로 정렬**해 한 화면에 둡니다(지금은 1·3단계로 분리되어 있고 좌표계도 다릅니다).
- **재생 헤드 하나가 두 트랙을 관통**합니다.
- 트랜스포트(재생·속도·볼륨·시크)를 **모든 단계에서 접근 가능한 고정 바**로 올립니다.
- **미입력 음절은 타임라인이 아니라 별도 "대기열" 레인**에 둡니다(지금은 x=0에 전부 겹칩니다).
- 타임라인 **클릭 = 해당 시각으로 이동**, 드래그 = 시작·끝 조절.

**7. 타이밍 정밀도 도구**

- **전역 오프셋 슬라이더**(±500ms, 실시간 미리보기 반영). `±10ms` 버튼 수천 번을 이것 하나가 대체합니다.
- **개인 지연 보정 마법사**: 클릭음 4회를 Space로 따라 찍게 해 사용자의 반응+출력 지연을 자동 산출 → 오프셋 기본값으로 제안.
- **재생 속도** 0.5× / 0.75× / 1× (`audio.playbackRate` + `preservesPitch = true`).
- **이벤트 시각 보정**: `audio.currentTime - (performance.now() - e.timeStamp)/1000`.

**8. 스탬핑 중 부분 갱신** — 입력 지연과 설정 초기화를 함께 해결합니다.

- `stamp()`가 `editor()`를 부르지 않고 **바뀐 노드만** 직접 조작: 다음 음절 텍스트, 해당 세그먼트 위치, 진행 카운터. DOM write 3회.
- **타임라인을 Canvas로 렌더**: 음절 500개 = DOM 500개 → 캔버스 1개. 미리보기와 같은 rAF 루프에 합류.
- A–B 구간·확대·볼륨을 **`project`나 세션 상태에 저장**해 재렌더에도 살아남게.
- `history.push`를 연속 스탬프 구간 단위로 묶고(coalesce), IndexedDB 저장에서 **변경되지 않은 Blob은 제외**.

**9. 작업 재개와 부분 확인**

- `stampIndex`를 프로젝트에 저장 + **"아직 타이밍이 없는 첫 음절로"** 버튼.
- `Backspace` 취소 시 **직전 음절의 `end`도 함께 복구**.
- **부분 타이밍 내보내기 허용** (미입력 음절은 회색 정적 표시 + `N개 미완료` 경고 배지).
- **구간 시험 렌더**: A–B 구간만 10–20초 렌더 → 4분을 기다리지 않고 확인.
- `history`/`step`/`stampIndex`/`selected`를 **프로젝트 전환 시 초기화** (지금은 다른 프로젝트를 열고 Ctrl+Z 하면 이전 프로젝트가 복원됩니다).
- 되돌리기를 **UI로 노출**: 상단 `↶ ↷` 버튼 + 되돌리기 토스트.

**10. 환경 제약 선고지**

- MP4 미지원 브라우저 안내를 **랜딩과 1단계**로 앞당깁니다(지금은 5단계).
- WebM 내보내기를 허용하고 **다운로드 확장자를 실제 `mimeType`과 동기화**합니다(현재 항상 `.mp4` 하드코딩).
- 내보내기 중 **탭 전환 금지 경고** (백그라운드에서 rAF가 멈춰 화면이 얼어붙은 영상이 됩니다).


**12. 다크 우선 편집 UI** — §3.3의 해결.

편집 화면을 중성 다크(`--bg: #15131d` 계열)로 전환해 **캔버스가 화면의 주인공**이 되게 합니다. `prefers-color-scheme` 대응 + 수동 토글. 결과물이 어두운 도구는 도구도 어두워야 색 판단이 됩니다.

**13. 버튼 위계 4종** — 전역 `button` 규칙을 제거하고 명시적 클래스로.

`primary` / `secondary` / `ghost` / `danger`. 비활성 버튼에는 **항상 이유를 함께** 표시합니다 (`타이밍 299/300 — 1개 남았어요`).

**14. 위치 의존 선택자 제거**

`.hero div` → `.hero-actions`, `.player div` → `.transport`, `.stamp div` → `.upcoming`, `.checklist div` → `.check-item`. 마크업과 스타일의 결합을 끊어야 **이후 개선이 가능해집니다.**

**15. 4단계를 3개 접이식 섹션으로** — `무대` / `글자` / `배경`. 캔버스는 상단에 고정해 모든 조작이 즉시 반영되는 것을 보이게 합니다.

**16. 프리셋 썸네일을 `renderFrame()`으로 그리기**

CSS 하드코딩 대신 실제 렌더러로 미니 프리뷰를 그리면 **색 불일치가 구조적으로 불가능해집니다**(§2.8). 동시에 프리셋을 진짜로 다르게 만듭니다 — 가사 위치(중앙/하단), 글자 크기, 배지 스타일, 진행바 유무까지 차등화.

### P3 — 완성도

- **마커 편집 UI** 추가 → 이미 구현된 인트로·간주·**카운트다운** 렌더 로직을 살립니다. 카운트다운은 노래방의 필수 요소입니다.
- **가사 2줄 줄바꿈** + 다음 가사에도 `fit()` 적용 + **배역 배지 폭 자동**(`measureText` 기반) + **배경 이미지 cover 계산**(종횡비 유지) + blur는 오프스크린 1회 전처리.
- **상단 메타·카운트다운에 외곽선** 추가.
- **미리보기 캔버스 `devicePixelRatio` 반영.**
- **접근성**: 재렌더 후 포커스 복원(`data-focus-key`), 파일 input 포커스 가능하게, `aria-current="step"`, 진행률 `aria-live="polite"`, 캔버스 `role="img"` + 설명, 대비 AA 확보, `prefers-reduced-motion` 대응, 정지 시 rAF 중단.
- **`alert()` → 인라인 토스트/배너**(`role="status"`), `#saved` 배지를 `저장 중` / `저장됨` / `실패` 3상태로.
- **영어·혼합 가사용 단어 단위 분리 모드** (현재 `Intl.Segmenter(ko, grapheme)` 고정이라 `Love`가 `L/o/v/e` 4스탬프가 됩니다).
